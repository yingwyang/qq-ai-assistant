积分是所有 AI 能力的「计量单位」：网页 AI 对话、群消息分析、语音合成都会扣积分，签到与月卡会发积分。
**任何一笔变动都会写一条流水**，所以「积分为什么少了」永远能查到具体那一笔。

## 积分变少了，去哪了？

**现象**：余额莫名其妙少了几百甚至上千，用户觉得自己「什么都没干」。

**原因**：AI 能力**用完即扣**，用户往往没有感知。按流水类型对照：

| 流水类型 | 触发动作 | 计费方式 |
|---|---|---|
| `AI_CHAT` | 网页 AI 对话 | 按 token：`max(5, ceil((输入×2 + 输出×4) / 1000))` |
| `AI_CHAT` | 对话里带图片 | 每张图 **+5** |
| `AI_CHAT` | 上下文超过前 10 条 | 超出的每条历史消息 **+1** |
| `AI_CHAT`（备注「群类型识别」） | 点「AI 识别群类型」 | 固定 **1** 分，**失败不扣** |
| `AI_ANALYZE` | 群消息分析 / 批量摘要 | `10 + 消息条数 × 1` |
| `TTS_SYNTHESIS` | 语音合成 | 每 **50 字 1 分**，最低 **2** 分 |
| `ADMIN_DEDUCT` | 管理员调账扣减 | 管理员手工指定 |
| `EXPIRE` / `REFUND` | 积分过期 / 失败退费与订单退款 | 按规则失效 / 正向回补 |

**处理步骤**

1. 让用户打开「个人中心 → 积分明细」，**按类型筛选**（AI 对话 / AI 分析 / 语音合成 / 管理员扣减…），再按「支出（OUT）」过滤；
2. 每行可见：类型、金额、扣费后余额、备注（含模型名、图片数、上下文条数）、关联 ID（会话 ID 或群号）；
3. 管理员可交叉核对后台「积分管理 → 积分流水」，支持按用户 ID、类型、方向、时间、金额区间、关联 ID 筛选并导出 JSON。

**验证**：用户流水的支出合计 = 余额减少量（按时间区间对齐）；备注里的模型名/会话 ID 能对应用户当时的操作。

```powershell
# 管理员查某用户的 AI 对话支出流水（需管理员 Cookie）
curl.exe -s -b cookie.txt "http://127.0.0.1:8081/api/credits/admin/transactions?userId=<用户ID>&type=AI_CHAT&direction=OUT&size=20"
```

> 提示：管理员的 AI 调用默认**免费**（`adminFree=true`），但仍会写一条 `amount=0` 的流水，备注带 `ADMIN_FREE`。看到 0 分流水不是故障，而是审计记录。

## 每日签到到底加了多少？

**现象**：签到到账积分与用户预期不一致：有人 150，有人 250/450/550；或某天只加基础分、没加月卡那份。

**原因**：签到到账 = **基础签到分 + 月卡每日加成**，两部分一起发：

| 组成 | 分值 | 说明 |
|---|---|---|
| 基础签到分 | **150**（`credit_rule.sign_in_points`，可配） | 所有用户都有 |
| 小月卡加成 | **+100** | 持有未过期小月卡 |
| 大月卡加成 | **+300** | 持有未过期大月卡 |
| 双持叠加 | **+400** | 小月卡 + 大月卡同时有效（100 + 300） |

关键细节：月卡加成**随签到发放**（不再在登录时静默发放），「签到只加 150」通常说明当前没有有效月卡；加成**幂等**，同一天只发一次——如果当天已通过旧逻辑拿过加成，这次签到**只发基础分**；月卡是否有效看订单（状态 `PAID` 且未过期）；同一天重复签到返回「今日已签到」；连续天数昨天签过则 +1，断签从 1 重新开始。

**处理步骤**

1. 用户在「积分明细」筛选类型 = **签到**，核对当天金额；
2. 再筛类型 = **月卡每日奖励**（`MONTHLY_CARD_DAILY`），备注写明月卡组合与加分数，如 `月卡每日签到奖励(ALL): +400`；
3. 签到只有基础分时：先确认该用户**是否有有效月卡**（订单管理按用户查）；若有月卡却无加成，看当天是否已有一条 `MONTHLY_CARD_DAILY` 流水（属预期的旧逻辑补发）；
4. 确实漏发时用管理员调账补回。

**验证**

```sql
USE qq_chat;
SELECT sign_in_date, points, streak_days FROM sign_in_record
WHERE user_id = <用户ID> ORDER BY sign_in_date DESC LIMIT 7;

SELECT type, direction, amount, balance_after, remark, created_at FROM credit_transaction
WHERE user_id = <用户ID> AND type IN ('SIGN_IN','MONTHLY_CARD_DAILY') ORDER BY id DESC LIMIT 10;
```

签到记录合计 = 基础分 + 实际发放加成；当天出现 `SIGN_IN` 与可能的 `MONTHLY_CARD_DAILY` 两条流水；签到日历显示当天已完成。

> 提示：月卡加成按**订单**判定，不依赖账号订阅等级字段。所以直购积分不会覆盖月卡权益，双持也一定叠加到 +400。

## 提示积分不足（402 / INSUFFICIENT_CREDITS）

**现象**：操作被拒绝，提示「积分不足，当前余额: X，需要: Y」；群类型识别直接返回 HTTP **402 Payment Required**（`errorCode = INSUFFICIENT_CREDITS`）；其它扣费接口返回 400 + 同一 `errorCode`。

**原因**：扣费走**悲观行锁**（`SELECT … FOR UPDATE`），余额不足时**直接失败，绝不会扣成负数**；余额校验发生在扣费那一刻，所以「预估够用」也可能因并发或实际 token 更多而不足；账户被标记「禁止消费」时返回的是另一条业务异常。

**处理步骤**

1. 确认余额与本次所需（前端对话会显示「本次将消耗约 X 积分」）：
   `curl.exe -s -b cookie.txt "http://127.0.0.1:8081/api/credits/balance"`
2. 让用户签到、等待月卡每日加成，或引导购买积分包 / 月卡；
3. 属于业务补偿的由管理员调账（下一节）；
4. 提示「账户已被禁止消费」时，检查该用户积分账户的 `consumption_banned` 标记并解除。

**验证**：重新操作成功且流水出现对应 OUT 记录；余额不为负，`balance_after` 与当前余额一致。

> 提示：调大「每日封顶」或配置月度免费配额可让高频用户在达标后**免费**（见下一节），但这是全局规则，会影响所有用户的成本，改动需谨慎。

## 管理员如何调账（有审计日志）

**现象**：需要给用户补发、退费或扣回积分，不知道在哪操作。

**原因**：管理员不能直接改数据库余额，必须走**调账入口**——它会写流水 + 记录操作人 + 写审计日志，保证可追溯。

**处理步骤**

1. 管理员登录 → 左侧「积分管理 → 用户积分」；
2. 搜索到目标用户，点「调整积分」；
3. 填写**金额**（正数=发放，负数=扣减）与**原因**（必填，写入流水备注且审计日志可见）；
4. 提交。也可用接口：

```powershell
curl.exe -s -b cookie.txt -X POST "http://127.0.0.1:8081/api/credits/admin/adjust" `
  -H "Content-Type: application/json" `
  -d '{"userId":<用户ID>,"amount":100,"reason":"<调账原因，会写入审计日志>"}'
```

5. 扣减时余额不足会直接报「积分不足」，**不会扣成负数**；
6. 查证：「积分管理 → 积分流水」筛选「管理员发放 / 管理员扣减」；「系统日志 → 审计日志」筛选 `CREDIT_ADJUST`，可见操作人、目标用户、金额与原因。

**验证**

```sql
USE qq_chat;
SELECT id, type, direction, amount, balance_after, remark, admin_user_id, created_at
FROM credit_transaction WHERE user_id = <用户ID> ORDER BY id DESC LIMIT 10;
```

流水新增 `ADMIN_GRANT`（IN）或 `ADMIN_DEDUCT`（OUT）且带 `adminUserId`；审计日志出现 `CREDIT_ADJUST`（摘要 `amount=… reason=…`）；用户侧「积分明细」能看到这笔变动。

## 每日封顶与阶梯折扣是怎么算的

**现象**：有人消费很多却不怎么扣分（甚至 0 分）；有人同样的操作扣得比自己算的少。

**原因**：最终扣费不是「单价 × 次数」，而是多层系数相乘：

```
cost = max(1, ceil(rawCost × 模型倍数 × 超配额倍率 × 月卡折扣 × 阶梯折扣))
```

| 机制 | 默认值 | 说明 |
|---|---|---|
| 月卡折扣 | 小月卡 0.9 / 大月卡 0.8 / 双持 0.7 | 按订单推导的订阅等级取值 |
| 阶梯累计折扣 | `≥1000 → 0.95`、`≥5000 → 0.9`、`≥20000 → 0.85` | 按**自然月累计支出**匹配，取最优惠一档 |
| 模型费率倍数 | `{"default":1.0}` | 可为贵模型单独设更高倍数 |
| 月度免费配额 | 0（关闭） | 当月 AI 对话次数少于配额时**本次免费** |
| 每日封顶 | 0（不限） | 当日累计支出 ≥ 该值时**本次免费** |
| 超配额倍率 | 1.5 | 配额耗尽后的加价倍率 |
| 最低消费 | 1 分 | 保底 1 分（免费场景除外） |

**处理步骤**

1. 解释某笔 0 分/低价流水 → 看流水备注标记：`ADMIN_FREE`（管理员免费）、`QUOTA_FREE`（月度配额内）、`DAILY_CAP_FREE`（每日封顶保护）、`/img:N`（图片费用）、`/ctx:N`（上下文增量）；
2. 需要调整机制时：管理员 →「积分管理 → 规则配置」修改并保存，**立即对新扣费生效，无需重启后端**；
3. 调整前评估影响面：每日封顶与配额是**全局的**，会直接改变所有用户的成本。

**验证**：改完规则让用户复现一次操作，对比流水金额与备注标记；阶梯折扣按自然月重置，跨月后累计支出清零、折扣回到 1.0。

> 提示：以上默认值来自「规则配置」页；若页面显示与本文不同，**以页面为准**（管理员可随时调整）。
