本页汇总管理后台最容易被误判的几件事：订单页「暂无订单数据」、订单状态看不懂、补单/退款/作废该用哪个、日志在哪看、改完配置要不要重启。

## 订单管理页明明有订单却显示「暂无订单数据」

**现象**：从「退款审批」或「纠纷处理」切回「订单管理」，列表显示「暂无订单数据」；手工清空筛选后订单又出来了。

**原因**：这三个页面**共用同一份筛选条件对象**（`statusSelected` 等）。「退款审批」进入时会把状态筛选改成 `PENDING_REFUND`，「纠纷处理」会改成 `DISPUTED`；历史上切回「订单管理」时**不还原**筛选，于是带着 `PENDING_REFUND` 去查订单——若当前没有待退款订单就显示空列表（看起来像"订单没了"，其实一条都没丢）。

**处理步骤**

1. **该问题已修复**：现在离开「订单管理」时会先把本页筛选存快照，切回时还原（含状态多选数组的拷贝），不再沿用其它页签留下的状态过滤；
2. 老版本上遇到时：把状态筛选清空（或改成「全部」）再点「搜索」，立刻恢复；
3. 升级到修复版本后按下面的方式验证。

**验证**：在「订单管理」设一组筛选（如状态=已支付）→ 切到「退款审批」→ 再切回，筛选与列表回到离开时的样子；「退款审批」页仍只显示退款审批中的订单（这是预期）。

```sql
-- 判断订单是否"还在"，用订单号直接搜比看列表更可靠
USE qq_chat;
SELECT order_no, status, plan_tier, price, credit_amount, created_at
FROM subscription_order ORDER BY id DESC LIMIT 10;
```

## 订单状态都是什么意思

**现象**：列表里的状态名看不懂，不知道哪一步该做什么。

**原因**：订单状态是固定枚举，含义与可执行动作如下。

| 状态 | 含义 | 可执行动作 |
|---|---|---|
| `PENDING` | 待确认收款（用户已提交订单，等待你核对到账） | 确认收款、作废 |
| `PAID` | 已支付，权益已发放 | 退款 |
| `PENDING_REFUND` | 退款审批中（用户提交了退款申请） | 同意退款、驳回退款 |
| `DISPUTED` | 纠纷中 | 处理纠纷（同意=退款 / 驳回） |
| `REFUNDED` | 已退款（积分已按比例扣回） | 仅查看 |
| `CANCELLED` | 已取消/作废（未确认收款的订单） | 仅查看 |
| `EXPIRED` | 已过期（超时未确认收款） | 仅查看 |

**处理步骤**

1. 按状态分派页签：待处理退款看「退款审批」，待处理纠纷看「纠纷处理」，其余在「订单管理」；
2. 「退款审批」「纠纷处理」页签标题带**待处理数量角标**，有角标就说明有活要干；
3. 点订单行打开详情抽屉，可看到该订单关联的**积分流水**（含退款流水）。

**验证**：处理完一笔后对应页签角标减 1；「订单管理」里该订单状态变为 `REFUNDED` / `PAID` / `CANCELLED`，与操作一致。

## 如何补单 / 退款 / 作废

**现象**：用户线下转账或付了钱但订单没生成，需要手工补；或要给已支付订单退款、把未支付订单作废。

**原因**：这三种都是**管理员特权动作**，各自对应不同接口与审计记录，走错会留下错误的账。

**处理步骤**

1. **补单**（用户已付款但没有订单）：「积分管理 → 订单管理」→ 右上角「+ 补单」，按下面的字段表填写；提交后生成一条 `PENDING` 订单，再执行「确认支付」把它变为 `PAID` 并**发放权益**。
2. **退款**（已支付订单）：在「订单管理」找到 `PAID` 订单 →「退款」→ 填写**原因**与**退款比例**（`refundRatio`，默认 `1.0` 全额）→ 提交后按比例扣回已发放积分，订单变为 `REFUNDED`。部分退款（比例 < 1）只扣回对应部分，请谨慎填写。
3. **作废 / 取消**（未支付订单）：`PENDING` 订单点「作废」，填原因后变为 `CANCELLED`。
4. **退款审批 / 纠纷处理**：「退款审批」页签对 `PENDING_REFUND` 订单执行同意或驳回；「纠纷处理」页签对 `DISPUTED` 订单选择同意（退款）或驳回并填写说明。

补单字段说明：

| 字段 | 说明 |
|---|---|
| 用户 ID | 必填，用户不存在会直接报错 |
| 套餐 | 直购积分（600 / 3500 / 16000 / 45000 / 100000）或小月卡 / 大月卡 |
| 金额（分，可选） | 覆盖默认价格，**单位是分**（如 990 = 9.90 元） |
| 赠送积分 / 时长天数（可选） | 覆盖套餐默认的积分数 / 月卡天数 |
| 订单号（可选） | 自定义订单号，便于对账 |
| 备注 | 建议写清来源（如「微信转账 + 截图」） |

```powershell
# 补单（金额单位：分；pointsGranted/durationDays 可省略以使用套餐默认值）
curl.exe -s -b cookie.txt -X POST "http://127.0.0.1:8081/api/credits/admin/orders/manual-create" `
  -H "Content-Type: application/json" `
  -d '{"userId":<用户ID>,"planCode":"SMALL_MONTH_CARD","remark":"<来源说明>"}'
# 确认支付（发放权益）
curl.exe -s -b cookie.txt -X POST "http://127.0.0.1:8081/api/credits/admin/orders/<订单号>/approve-payment"
```

**验证**：每类操作都会写审计日志——补单 `ADMIN_MANUAL_ORDER`、确认支付 `ADMIN_APPROVE_PAYMENT`、强制退款 `ADMIN_REFUND_ORDER`、作废 `ADMIN_CANCEL_ORDER`；退款后用户在「积分明细」能看到 `REFUND` 流水；补单 + 确认支付后积分/月卡立即生效。

> 提示：**先补单再确认支付**，不要只补单就交付用户——`PENDING` 订单不会发放任何权益。

## 积分流水与审计日志在哪看

**现象**：需要查「这笔积分是谁扣的 / 谁改的」「管理员做过什么操作」，但不知道入口。

**原因**：系统把「积分变动」与「管理操作」分成两个独立可追溯体系。

| 要查的东西 | 入口 | 内容 |
|---|---|---|
| 积分流水 | 「积分管理 → 积分流水」 | 类型、方向（收入/支出）、金额、变动后余额、备注、关联 ID、操作人 |
| 审计日志 | 「系统日志 → 审计日志」子页签 | 操作人、动作、目标、结果、时间 |
| 应用日志 | 「系统日志 → 应用日志」子页签 | 即 `backend/logs/application.log` 的在线查看（可按级别过滤） |

**处理步骤**

1. 查积分：进入「积分管理 → 积分流水」，可按 **用户 ID、类型、方向、关联 ID、时间区间、金额区间** 筛选，并可「导出 JSON」做对账；
2. 查管理操作：进入「系统日志」→「审计日志」子页签，按动作或目标搜索；
3. 常用审计关键字对照：

| 场景 | 关键字 |
|---|---|
| 管理员调账 | `CREDIT_ADJUST` |
| 重置用户密码 / 禁用启用用户 | `ADMIN_RESET_PASSWORD` / `USER_ACTIVE_CHANGE` |
| 角色变更 / 删除用户 | `ROLE_CHANGE` / `USER_DELETE` |
| 补单 / 支付 / 退款 / 作废 | 见上一节 |
| 启动 / 停止组件 | `COMPONENT_START` / `COMPONENT_STOP` |

4. 需要更细的技术细节（异常堆栈等）时直接看文件：

```powershell
cd D:\ai\Documents\qq-web\qq-ai-assistant\backend
Select-String -Path logs\application.log -Pattern 'ERROR' | Select-Object -Last 30 | ForEach-Object { $_.Line }
```

**验证**：刚做完的操作能在 30 秒内出现在审计日志里（操作人=你自己）；积分流水的「变动后余额」按时间顺序连续自洽。

> 提示：应用日志按天滚动，单文件超过 20MB 会切分，最多保留 14 天 / 总量 500MB（见 `backend/src/main/resources/logback-spring.xml`）。更早的日志需要从备份里找。

## 修改配置后要不要重启

**现象**：在「配置管理」页改了 Token 或地址，保存后好像没生效；有的配置项旁边有「需重启」小标签，有的没有。

**原因**：两类配置的生效方式不同。

| 类型 | 例子 | 生效方式 |
|---|---|---|
| 带「需重启」标签 | `astrbot.token`、`napcat.token`、`napcat.webhook-token`、`gpt-sovits.token`、`minio.access-key`、`minio.secret-key`、`jwt.secret`、`jwt.expiration` | 保存后**必须重启后端**才真正生效 |
| 不带标签 | `astrbot.api-url`、`napcat.api-url`、`gpt-sovits.api-url`、`minio.endpoint` | 保存即写入运行时属性 |

保存动作会做两件事：写入运行时属性 + 落盘到 `backend/data/application-override.properties`。但已注入到各服务里的值（如调用 AstrBot 用的 token/地址）是在**后端启动时**读取的，所以「不带标签」的项在运行中修改也可能不生效。

**处理步骤**

1. 改完配置后**统一重启后端**（最稳、最省事）；
2. 涉及 JWT 的项（`jwt.secret` / `jwt.expiration`）改完必须重启，且会造成**所有人登录态失效**，需提前通知；
3. 只有改「积分规则配置」无需重启：规则保存在数据库并刷新内存缓存，保存后立即对新扣费生效；
4. 重启前确认没有正在进行的批量任务（如批量补摘要）；重启不会丢消息，但队列任务要等消费者重新连上。

**验证**

- 重启后进入「配置管理」，确认修改后的值已保存（密钥类显示 `***`，属正常掩码）；
- 改了 `napcat.webhook-token` 后：群里发一条消息 → 后端日志出现「【根路径】收到NapCat消息」且**没有** `Webhook Token 验证失败`；
- 改了 `astrbot.token` 后：触发一次摘要，日志不再出现 `AstrBot 返回错误响应` / 鉴权失败。

> 提示：`napcat.webhook-token` 两侧必须一致——后端改了、NapCat 侧 `onebot11_<QQ>.json` 里的 token 没改，就会 401 拒收所有消息。改完记得两边同步（后台「组件控制」的 NapCat 自动配置会按后端配置重写一份）。
