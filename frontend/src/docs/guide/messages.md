这一页解释两件事：**消息是怎么进来的（含去重规则）**，以及**图片/视频/语音为什么有时是占位提示**。看完你能自己判断「这是正常等待，还是真的没救回来」。

## 消息从 QQ 到网页的路径

1. 机器人 QQ 号收到群消息，NapCat 通过 Webhook 上报给后端（8081）。
2. 后端校验上报令牌，令牌不对直接拒绝（401）。
3. 只接受**群消息**：`post_type` 为 `message` 或 `message_sent`、且 `message_type` 为 `group`。其它一律丢弃。
4. 解析出群号、发送者 QQ、昵称、发送时间与消息原文（CQ 码形式），识别消息类型。
5. **去重**：按「群号 + 消息 ID」判断这条消息是否已经存过。
6. 消息落库到 MySQL；如果消息里带媒体，再向 RabbitMQ 投递下载/转码任务。
7. 媒体下载完成后再回填消息记录，并通过 WebSocket 推给页面——你看到的图片就是这一刻出现的。

## 去重规则

| 项目 | 规则 |
|------|------|
| 判重字段 | **群号 + 消息 ID 组合**（不是按时间，也不是按自增 ID） |
| 为什么按群判重 | QQ 的消息 ID 只在群内唯一，跨群可能重复，只按 ID 判会丢消息 |
| 重复上报的结果 | 不入库、不重复下载媒体、不重复投递任务，直接返回「已存在」 |
| 兜底 | 数据库唯一约束冲突时同样按「已存在」处理，不会报错给你 |
| 消息 ID 缺失时 | 用当前时间戳充当，实际上等于无法去重（极少发生） |

> 提示：NapCat 侧配置重复上报、或后端重启后收到补发，都不会产生重复消息——这是去重规则在起作用。

## 哪些消息会被记下来

| 消息 | 是否入库 | 说明 |
|------|----------|------|
| 群聊文本消息 | 记录 | 支持 Markdown 风格显示与自动链接 |
| 图片 / 视频 / 语音 | 记录 + 下载媒体 | 见下一节 |
| @ 提及 | 记录 | 显示为 `@昵称`，取不到昵称时显示 `@QQ号` |
| 回复消息 | 记录 | 显示被引用的原文 + 回复内容 |
| 合并转发（聊天记录） | 记录 | 折叠为「聊天记录」卡片，点击展开 |
| 小程序 / 卡片消息 | 记录 | 作为应用消息展示 |
| **机器人自己发的消息** | 记录 | 会标记为自己发送，和他人消息样式区分 |
| **私聊消息** | **丢弃** | 系统只处理群消息 |
| **撤回、戳一戳等通知事件** | **丢弃** | 不生成任何消息记录 |

> 提示：入库的是消息原文（含 CQ 码），界面上的「纯文本」是前端解析出来的。解析不出可读内容时会显示 `[不支持的消息类型]`。

## 媒体怎么下载、放在哪

| 类型 | 是否下载实体 | 存储位置（相对项目根目录） | 是否需要转码 |
|------|--------------|---------------------------|--------------|
| 图片 | 下载 | `backend/uploads/images/images/{群号}/{日期}/` | 否 |
| 视频 | 下载 | `backend/uploads/images/video/{群号}/{日期}/` | 否 |
| 语音 | 下载 | `backend/uploads/images/voice/{群号}/{日期}/` | **是**：SILK/AMR → MP3 |
| 音频、文件（如文档/压缩包） | **只记录消息类型，不下载实体** | — | — |

下载时按「直连取源 → 让 NapCat 取文件 → （仅视频）缩略图兜底」三级尝试。语音转码优先用 FFmpeg，失败时回退到 Python 的 SILK 解码脚本；转码成功后原始文件会被删除，只保留 MP3。

体积上限（超过就放弃下载，界面出现占位提示）：

| 类型 | 默认上限 | 对应配置项 |
|------|----------|------------|
| 图片、语音等普通媒体 | 100 MB | `FILE_DOWNLOAD_MAX_MB` |
| 视频 | 300 MB | `FILE_DOWNLOAD_MAX_VIDEO_MB` |

> 提示：任务失败会重试 3 次（间隔 1s → 2s → 4s），仍失败则进入死信队列。管理员可在 RabbitMQ 管理界面（`http://localhost:15672`）看到 `media.download.dlq` 与 `voice.transcode.dlq`。

## 各种占位提示是什么意思

界面上看到的提示分三种状态，含义完全不同：

### 一、正在处理（正常，稍等即可）

| 显示 | 含义 |
|------|------|
| `图片下载中...` | 图片任务还在队列里或正在下载 |
| `视频下载中...` | 同上（视频体积大，通常更慢） |
| `语音转码中...` | 语音正在做 SILK → MP3 转码 |

### 二、已放弃下载（需要人工处理）

系统在放弃下载时会把消息内容改写成固定占位符，界面按类型显示为：

| 数据库里的占位符 | 界面显示 | 触发原因 |
|------------------|----------|----------|
| `[图片已过期]` | `图片已删除` | 图片取源失败、超过 100MB 或被安全策略拦截 |
| `[视频已过期]` | `视频已删除` | 视频原片在 QQ 侧已不存在、超过 300MB 或被拦截 |
| `[媒体已过期]` | 按类型显示 | 其它媒体的兜底占位（正常链路很少出现） |
| `[语音转码失败]` | `[语音转码失败]` | 语音下载到了，但 FFmpeg 与 Python 解码都失败 |

### 三、文件真的没了（历史上存在过，现在读不到）

| 显示 | 含义 |
|------|------|
| `图片已删除` / `视频已删除` | 记录里的文件路径在服务器上已不存在（被清理或删除） |
| `音频已删除` | 同上，语音文件被删除 |
| `消息已删除` | 这条消息被（软）删除过，只保留记录标记 |

> 提示：看到「已过期/已删除」类提示时，消息本身的文字记录仍在，只是媒体文件取不回来了。删掉的消息不会自动恢复，但可以重新让群友发一次。

## 视频只显示一张图：`原视频未缓存，仅预览`

这是**降级成功**，不是失败。原因和解法：

1. QQ（NT 版）默认**不在本地保存视频原片**，只留一张几十 KB 的缩略图；原片只有在该客户端真正播放过之后才存在。
2. 后端三级取源全部失败后，会去 QQ 的本地目录里找这张缩略图，找到就落盘作为预览图。
3. 界面上会把这张图渲染成图片，左下角标注 `原视频未缓存，仅预览`，点击可以放大查看。
4. 想要**能播放的原片**，可以：让群友在原手机上把视频点开播放一次后重新发送；或升级 NapCat 后重发；或请管理员确认 `FILE_DOWNLOAD_MAX_VIDEO_MB` 没有被设小。
5. 如果连缩略图都找不到（日志会写「视频原片缺失且未找到缩略图」），界面就只剩 `视频已删除` 占位。

## 在页面上怎么操作这些媒体

| 类型 | 操作 |
|------|------|
| 图片 | 点击缩略图放大预览；预览层里可左右切换、按 `Esc` 关闭 |
| 视频 | 有播放器就直接播放；是预览图则点击放大 |
| 语音 | 点击 QQ 风格语音气泡播放，气泡上显示时长；未转码的记录会先触发一次按需转码 |

## 消息会保存多久

| 阶段 | 默认行为 |
|------|----------|
| 常规保存 | 消息长期保留在数据库，媒体文件长期保留在磁盘 |
| 自动归档 | 每天凌晨 2 点把 **90 天前**的消息写入归档 JSON 文件（`backend/uploads/archive/`），并标记为已归档 |
| 归档后的清理 | 归档满 30 天（即约 120 天前）的记录会从数据库删除 |
| 注意 | 归档**只搬消息记录，不动媒体文件** |

> 提示：归档天数与执行时间由 `archive.days-before` 与 `archive.cron` 控制，需要调整请找管理员。

## 常见问题

| 现象 | 原因与处理 |
|------|------------|
| 语音点了没反应，提示「音频地址为空」 | 该条语音没有可播放文件，属占位记录 |
| 提示「语音转码失败」 | FFmpeg 路径或 Python 解码脚本不可用，请管理员看后端日志 |
| 图片一直在「下载中」不变化 | 队列积压或消费者没运行；请管理员查 RabbitMQ 的 `media.download.queue` 深度并重启后端 |
| 大量图片同时变「图片已删除」 | 媒体目录不可写、磁盘满，或 NapCat 令牌失效，请管理员排查 |
| 别人的电脑上打开，媒体都加载不出来 | 媒体地址按后端本机 `8081` 拼接，跨机访问需要管理员用反向代理/域名统一入口 |
| 消息只显示 `[不支持的消息类型]` | 该消息是卡片、位置等特殊类型，前端没有对应的展示样式 |
